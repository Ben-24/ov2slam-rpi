Read rpi_cam_stereo.yaml
Here's how the scalar parameters in OV2SLAM relate to the standard camera matrices:

Camera (Intrinsic) Matrix K
The camera matrix maps 3D camera-space points to 2D image pixels:


K = [ fx   0   cx ]
    [  0  fy   cy ]
    [  0   0    1 ]
In your file:

Camera.fxl = 458.654 → focal length in pixels along X
Camera.fyl = 457.296 → focal length in pixels along Y
Camera.cxl = 367.215 → principal point X (optical center column)
Camera.cyl = 248.375 → principal point Y (optical center row)
Projection formula: [u, v, 1]ᵀ = K * [X/Z, Y/Z, 1]ᵀ

Distortion Coefficients D
Real lenses distort light. OpenCV's plumb-bob model (used here) has:


D = [k1, k2, p1, p2 (, k3)]
k1, k2 (Camera.k1l, Camera.k2l) — radial distortion (barrel/pincushion). Applied as: r² = x² + y², correction ≈ (1 + k1·r² + k2·r⁴)
p1, p2 (Camera.p1l, Camera.p2l) — tangential distortion (lens not perfectly parallel to sensor)
These are applied before the camera matrix, to correct the raw distorted pixel coordinates back to ideal pinhole positions.

Projection Matrix P (stereo, 3×4)
Used after stereo rectification. It combines K with the stereo baseline:


Left:   P = [ fx   0   cx    0  ]
            [  0  fy   cy    0  ]
            [  0   0    1    0  ]

Right:  P = [ fx   0   cx  -fx·Tx ]
            [  0  fy   cy    0    ]
            [  0   0    1    0    ]
Where Tx is the baseline (distance between cameras). Your file sets bdo_stereo_rect: 0, so OV2SLAM is using the raw camera matrices + distortion directly rather than rectified projection matrices.

Summary Flow

3D World Point
      ↓  (extrinsic: body_T_cam0 / body_T_cam1)
3D Camera Point [X, Y, Z]
      ↓  (divide by Z → normalized coords)
Normalized [x, y] = [X/Z, Y/Z]
      ↓  (apply k1, k2, p1, p2 distortion)
Distorted [x', y']
      ↓  (apply K: fx, fy, cx, cy)
Pixel [u, v]
The extrinsic body_T_cam0/body_T_cam1 are the 4×4 rigid-body transforms you see in the file — they're separate from calibration intrinsics.

Now the code tells the exact story. Look at slam_params.cpp:87:


T_left_right_ = Sophus::SE3d(Tbc0.inverse() * Tbc1);
That's the only thing OV²SLAM ever does with both matrices. It immediately combines them into a single camera-to-camera transform. The "body" frame is purely mathematical scaffolding that cancels out:


T_left_right = Tbc0⁻¹ × Tbc1
             = T_cam0_body × T_body_cam1
             = T_cam0_cam1
So body_T_cam0 and body_T_cam1 are just two ways of expressing the stereo geometry — the rotation and translation between your two cameras. The "body" label is inherited from EuRoC/IMU conventions but OV²SLAM doesn't use the body frame for anything else.

What this means practically:

Only the relative values matter, not the absolute ones. These two setups are equivalent:


Option A (calibrate_stereo.py convention):
  body_T_cam0 = Identity
  body_T_cam1 = [R | T]         ← R,T from stereoCalibrate
  → T_left_right = I⁻¹ × [R|T] = T_cam0_cam1  ✓

Option B (README/Kalibr convention):
  body_T_cam0 = T_cn_cnm1       ← from Kalibr camchain.yaml
  body_T_cam1 = Identity
  → T_left_right = T_cn_cnm1⁻¹ × I = T_cam0_cam1  ✓
The current EuRoC values still worked for EuRoC because their body (IMU frame) cancelled out correctly — but they encode the wrong stereo geometry for your RPi cameras and need to be replaced with your actual calibration output.

2. Significant vertical offset between cameras
The board appears at different heights in left vs right, suggesting the cameras aren't parallel — they're pointing in slightly different directions. This also explains the 40-degree off-diagonal values in the rectification matrix from your ost.txt.

3. Why 11×7 found more pairs but got 50px error
With the wrong grid size, some images get "false positive" detections (finding a sub-pattern). With the correct 11×7 size, more real detections occur, but the camera views are so different that OpenCV assigns corners in opposite orders (180° flip) between left and right — which destroys stereo calibration.
